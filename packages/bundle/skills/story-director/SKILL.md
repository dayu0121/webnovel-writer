# 短故事总控（Story Director）

短故事以一篇完整故事为生产单位，不伪装成“一章长篇”。主 Agent 负责调度、证据核对和作者裁决；正文生成与语义审读交给自包含子代理。

## 第一律：从真实文件校准

1. 作者明确短故事或 `story_*` 工具时，先调 `story_get_status`；换会话、换故事、改稿后都重新查。
2. 有 `storyId` 后先 `story_select`，不得沿用上一轮聊天里的故事；确认 `平台: fanqie` 与 `规则包: fanqie-short-story@1`。
3. 当前项目只接受番茄短故事；不得创建、改写或声称支持其他平台/通用规则包。状态建议只作定位器；工具失败、hash 冲突或文件异常时停下核对，不自行绕过。
   默认目标范围：超短篇 8000-24900 字；中短篇 25000-80000 字；自定义目标仍必须标记为番茄短故事。范围来自规则包记录的活动公开口径，活动变化时不得沿用旧活动结论。
4. 长篇请求用 `novel_*`；短故事请求用 `story_*`。不得把卷、章、章号带入短故事工具。

## 路由表

| 位置 | 动作 |
| --- | --- |
| 故事卡准备 | 整理标题、篇幅档案、核心钩子、主角欲望、核心冲突、情绪承诺、结局方向、风格与禁区；按 `fanqie-short-story@1` 调 `story_write_plan` |
| 蓝图待确认 | 把作品卡和蓝图 hash 完整呈给作者；作者确认后原样调 `story_confirm_plan` |
| 可写 | 组装自包含起草任务包，派子代理生成整篇；结果只用 `story_write_draft` 落为待审稿 |
| 起草中 | 核对是否已有唯一待审稿；没有则继续起草，不同时保留两份待审稿 |
| 待审 | 加载《短故事审读》，逐模块派发并用 `story_record_review` 回写；空发现项也回写 |
| 修订中 | 逐项呈报处置；新稿和处置用 `story_apply_revision` 同批落盘；改文后必须重审 |
| 定稿候选 | 调 `story_prepare_delivery`，呈报字数、阻断和提醒 |
| 可交付 | 取得正文、审读、交付三个 hash 后调 `story_settle`；批准弹窗必须展示三个 hash |
| 已定稿 | 需要交付文件时先 `story_compute_export` 预览，原样携带 `finalHash` 经 `story_write_export` 写 MD/TXT |
| 已导出 | 汇报实际目录、文件、冲突和写后校验；不声称已经投稿或发布 |

## 两个作者门

1. **蓝图门**：故事卡与一页蓝图确认后才允许写正文。
2. **交付门**：最终正文、当前审读记录和交付检查的 hash 绑定后批准定稿。

作者明确说“按已确认蓝图写到可交付，中间自行推进”时，机械的起草、审读、修订和检查可连续执行；新创作选择、重大改向、作者保留/驳回的发现项、工具冲突仍须停稳。

## 子代理交接

- 起草包内联：作品卡、完整蓝图、篇幅档案、文风/禁区、硬约束、目标读者和输出格式。
- 审读包内联：当前待审稿全文、故事卡、蓝图、篇幅档案、规则包和发现项 JSON 格式；不给子代理书仓写权限。
- 子代理只返回正文或结构化发现项。落盘、审读回写、处置和定稿全部由主 Agent 调专用工具。

## 真源与导出纪律

- `故事.json`、已确认作品卡/蓝图、检查记录、定稿由专用工具维护。
- 草稿可以多版本留档，但待审稿必须唯一。
- 不手改 `检查/*.json`，不覆盖定稿，不用卷01/第0001章伪装短故事。
- 平台规则包必须有来源、版本、hash 和适用范围；本项目固定使用 `fanqie-short-story@1`。官方资料缺失或活动边界不明确时，只报告已核对的番茄通用口径，不冒充具体活动合规结论。
- 投稿、邮箱提交和平台发布由作者手工完成；工作台只准备交付文件。
