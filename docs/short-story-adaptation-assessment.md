# 番茄短故事改造评估

> 评估对象：Webnovel Writer v8，基线提交 `5d81b8a235411e6cc9472551857eb2983b677610`。
> 平台资料核对日期：2026-09-25。
> 本文是改造决策依据，不是番茄官方规则副本，也不是实施排期；当前内置规则包见 `docs/user/fanqie-rule-pack-v1.md`。

## 结论

**可以改，且底层工程很值得复用；但不能只换术语或目录名。**

推荐路线是：

> 保留本地文件真源、Git、事务、作者确认、审核证据、版本恢复和安全门禁；新增独立的短故事领域层，重写卷章状态机、工具协议、写作技能、审读、检索、界面和导出。

不建议把现有长篇项目全局改写成“所有地方都只剩一章”。那会让分卷、章号、卷对账等旧耦合继续渗入新领域。正式产品应让“一篇短故事”成为一级内容单元；场景或节拍只作为蓝图内部的可选规划粒度。

## 番茄短故事公开规则能确认什么

以下只记录官方公开页面明确写出的内容。具体活动会变化，工作台不应把某次活动规则硬编码成永久平台规则。

### 篇幅和交付

番茄短故事 2026 年第二期“千字万金”官方说明将作品区分为：

- 超短篇：8000—24900 字
- 中短篇：25000—80000 字
- 分类按首次投稿字数判定

官方 2026 年活动全览还强调：

- 适合新媒体渠道阅读习惯
- 情绪浓度高、节奏紧凑、爆点密集
- 中短篇要篇幅充足、结构完整、情节具有延展性
- 优质作品可能进入短漫剧、短剧等改编通道
- 不得通过恶意水字数、章节重复、抄袭、异常引流等方式获取奖励

“哥伦布计划”使用“1 万字左右超短、3 万字左右中短篇”的活动口径。这是该活动的投稿口径，不应覆盖上面的通用分类。

来源：

- [2026 番茄短故事激励活动全览](https://fanqienovel.com/writer/zone/article/7685973837409697854)
- [番茄短故事 2026「千字万金」五百万激励计划第二期](https://fanqienovel.com/writer/zone/article/7621764547262545982)
- [番茄短故事 2026 西方题材赛道「哥伦布计划」](https://fanqienovel.com/writer/zone/article/7637809338446266430)

### 创作方向

官方短故事课堂反复提到的创作方向包括：

- 开篇尽快建立具体危机或强冲突
- 人设逻辑稳定，金手指负责预警、线索或辅助，不替主角代打
- 用生活细节、财产、关系、规则和具体场景承载矛盾
- 小冲突持续推进，关键节点集中释放情绪
- 主角有清晰行动和选择，不能长期只受辱或只被推着走
- 结尾不仅完成反转，也要完成关系、价值或人物秩序的收束
- 兼顾新媒体阅读与后续短剧、漫剧改编延展性

这些是创作指导，不是可以机械判定的合规门槛。来源：

- [短故事作家课堂：四大热门方向爆款拆解与创作指南](https://fanqienovel.com/writer/zone/article/7670363158518693950)
- [拆解世情短故事热门元素组合](https://fanqienovel.com/writer/zone/article/7683816556886753342)
- [短故事改编风向标：8 月宝典](https://fanqienovel.com/writer/zone/article/7678898394189791256)

### 产品设计上的直接结论

1. 短故事产品的主对象应是“故事”，不是“卷章”。
2. 目标篇幅应是可配置的 `ultra-short` / `mid-short` 档案，而不是固定 1000 字下限。
3. 审读重点应从“章末钩下一章”改为“开篇钩子、升级节点、关键转折、高潮、结局、完整闭环”。
4. 平台规则必须版本化，记录来源、版本、适用活动和生效时间。
5. 没有平台规则包时，产品只能声称做了通用质量检查，不能声称“符合番茄要求”。
6. 发布、投稿和邮箱投稿继续由作者手工完成，工作台负责准备合规的交付文件和检查报告。

## 推荐的短故事产品

### 产品主流程

```text
灵感
  → 故事卡准备
  → 蓝图待确认
  ── Gate A：作者确认故事卡与蓝图 ──
  → 起草中
  → 待审
  ⇄ 修订中
  → 定稿候选
  → 交付检查
  ── Gate B：作者确认正文、审读处置和检查报告 ──
  → 可交付
  → 已导出
  → 已归档
```

常规写作只保留两个作者门：

1. **蓝图门**：确认故事卡、篇幅档位、核心冲突、主要转折和结局方向。
2. **定稿门**：确认具体正文 hash、审读记录 hash、交付检查报告 hash。

机械的草稿、审读、修订和报告组装可以连续执行；覆盖已交付正文、补偿历史、导出到工作区外等不可逆动作继续单独确认。

### 轻量故事卡

建议字段：

- 标题与一句话卖点
- 题材、主分类、目标读者
- 篇幅档位与目标字数区间
- 核心钩子
- 主角核心欲望与底线
- 核心冲突及对手/阻力
- 主要情绪承诺
- 关键转折与结局方向
- 叙述视角与文风
- 创作禁区
- 是否面向短剧/漫剧改编

### 一页故事蓝图

建议只保留对成稿真正有用的结构：

- 开篇钩子与首个冲突
- 2—5 个升级节点
- 关键证据或真相
- 中段主动选择
- 高潮场景与情绪释放
- 结局及闭环
- 人物逻辑和关系变化
- 信息边界
- 可选场景卡

### 全篇审读

建议把现有八维长篇审读改成：

1. 开头吸引力
2. 故事因果与升级
3. 人物目标、行动与逻辑
4. 情绪曲线和爆点密度
5. 转折、高潮、结局闭环
6. 事实、称谓、时空和设定连续性
7. 文风、视角、重复表达和 AI 痕迹
8. 篇幅、交付格式和改编延展性

其中篇幅、重复段落、未完成标记、平台模板等可以由确定性脚本检查；语义质量继续由子代理审读。

### 交付检查

检查结果分两级：

- **阻断**：空稿、占位符未清理、审读证据过期、硬约束失败、结局缺失、目标文件与批准稿 hash 不一致。
- **提醒**：偏离目标字数、开头进入偏慢、情绪峰值不足、重复表达、结尾余味偏弱、可选 IP 延展性建议。

提醒不能伪装成平台硬规则。阻断项必须为零，警告项允许作者显式接受。

## 推荐的故事仓

```text
<故事目录>/
  故事.json
  作品卡.md
  蓝图/
    故事蓝图.md
    人物表.md
    设定.md                 # 可选
  正文/
    草稿/
      v001.md
      v002.md
    定稿/
      r001.md
  检查/
    审读记录.json
    交付检查.json
    导出记录.json
  .gitignore
  .git/
```

`故事.json` 只保存身份、格式版本和配置，不保存第二套可变工作流状态：

```json
{
  "schemaVersion": 1,
  "kind": "short-story",
  "formatVersion": 1,
  "storyId": "s-...",
  "title": "故事标题",
  "target": {
    "profile": "ultra-short",
    "minChars": null,
    "idealChars": null,
    "maxChars": null,
    "counting": "codepoint"
  },
  "rulePack": {
    "id": "generic-quality",
    "version": 1
  },
  "platformProfile": null
}
```

工作流位置仍从实际文件、版本、hash 和检查记录现算，不额外维护一个可能漂移的 phase 数据库。

## 两种实施路线

### 路线 A：验证型 MVP

用一个短故事 façade 暂时把内部物理布局映射为 `卷01 / 第0001章`，但：

- 界面、技能和工具参数不出现卷章
- 不走原长篇 11 步生产链
- 只复用草稿版本、审核指纹、事务写入和 Git
- 新增短故事专用状态推导与导出
- 导出不得带伪卷章标题

优点是改动较小，适合验证“两次确认的一次性闭环”。缺点是仍背着临时 schema 债务，不适合作为最终格式。

### 路线 B：正式产品

直接建立 `short-story-v1` 故事仓和故事级领域层，旧长篇格式保留为 legacy 模式。

优点是边界干净，后续维护成本低。缺点是核心、工具、技能、检索、UI 和测试需要成套改造。

**建议：先用三篇合成短故事验证路线 A 的产品流程；验证通过后实施路线 B，不把临时映射当成最终数据格式。**

## 分阶段建议

### M0：冻结短故事产品契约

- 冻结故事卡、蓝图、篇幅档案、检查分级和两个作者门
- 建立通用质量规则包与平台规则包的双层结构
- 为超短、中短和不同题材准备合成样本

验收：所有规则能追溯来源类别；没有无来源的“番茄官方阈值”。

### M1：短故事验证闭环

- 故事创建、选择、书架和状态恢复
- 一页蓝图、整篇草稿、整篇审读、修订
- 轻量连续性检查
- 无伪卷章的 MD/TXT 导出
- 旧长篇工具和 UI 不向短故事暴露

验收：两篇故事互不串状态；新会话可恢复；Gate B 后导出与批准稿一致。

### M2：原生故事仓

- `short-story-v1` manifest、路径和 schema codec
- 故事级 scan/progress/recovery
- legacy-longform 与 short-story 并存
- 不自动迁移或猜测旧书类型

验收：未知 schema 失败关闭；并发写、崩溃恢复和迟到审读仍保持 fail-closed。

### M3：审读与交付规则包

- 全篇八维审读
- 阻断/提醒级检查
- 规则来源、版本和适用活动绑定
- 内容变化自动使旧检查过期

验收：同一输入的确定性检查可复验；无平台 profile 时只显示通用检查。

### M4：短故事 Web 主路径

- 故事仪表盘
- 字数与篇幅档位
- 蓝图节点完成度
- 审读和交付报告
- 复制、下载、MD/TXT 导出
- 桌面完整可用，窄屏可读写和导出

验收：关键路径在窄屏无横向溢出；导出无伪卷章；目标冲突时不覆盖旧文件。

### M5：格式与可选平台适配

- DOCX/PDF
- 活动专属模板和规则包
- 可选合集导出
- 平台 profile 缺失时明确禁用并说明原因

自动投稿、云同步和真正跨手机编辑不应混入这一阶段。跨手机需要独立解决认证、加密、同步游标、离线编辑和冲突合并，不是加几段响应式 CSS。

## 改造前应先修的现有接缝

这些问题不属于短故事专属需求，但短故事会放大它们：

1. **组包没有硬性要求当前审核完成。**`packages/core/src/prepare/pack.ts` 的 `computePack` 只要求唯一待审稿。短故事 Gate B 应同时校验审读完成、未过期、处置完整和正文 hash。
2. **批准提示没有展示包 hash。**`novel_settle_chapter` 的 ask 只带卷/章名范围。批准等待期间包若被重建，旧批准可能对应新内容。短故事批准应绑定故事、正文、审读和检查报告 hash。
3. **生产润色没有直接接入 `@webnovel/polish`。**当前生产技能主要让子代理通过通用文件写工具落稿，代码级唯一待审稿和保真约束没有成为常驻硬门。短故事版应把关键不变量移进受信写入工具。
4. **通用草稿门禁只约束路径形状。**它会如实播报材料和细纲状态，但不会阻止跳过流程直接写草稿。短故事产品若需要强流程，应由专用草稿工具执行。
5. **最小设计 seed 会用空正文标记已确认。**它适合测试和走查，不应成为面向作者的“一键生成好故事”体验。
6. **完整生产 E2E 停在定稿裁决前。**`packages/core/tests/min-chain.spec.ts` 没有覆盖普通 bundle 的批准→沉淀→导出→下一单元闭环。
7. **审读底本存在无来源经验阈值。**`章节结构审读.md` 的“短篇基础线 1000+”和 `节奏与张力审读.md` 的“番茄风格对话密度 1.5”不应作为合规门槛。应删除、标成非平台通用软信号，或迁入带来源和版本的规则包。
8. **书 id 碰撞缺少显式检查。**当前 `generateBookId` 使用短 djb2。短故事数量可能远高于长篇书仓，建议改用随机稳定 id，或至少建仓时扫描重复并拒绝。
9. **非空沉淀的补提交幂等不足。**时间线、账本和世界书事实按现有文件追加；若业务文件已落盘而 Git 提交失败，重跑可能再次追加同一章事实。短故事沉淀应给每个候选记录来源 receipt，并按“来源 hash + 目标路径”跳过已落位内容。
10. **定稿不是文件、裁决、Git 和读者视图的端到端原子事务。**批准先单独写入清单，正文和账本再批量落盘，Git 最后提交；不取锁的读者还可能在多次 rename 之间看到半批状态。`scanChapter` 只以定稿文件存在判断完成，文件已写但 `ch:` 缺失时可能先显示完成。
11. **“旧待审稿降级 + 新稿写入”有三条非原子路径。**`packages/polish/src/run.ts`、`packages/core/src/revise/apply.ts` 和 `packages/drafting/src/write.ts` 都先降级再写新稿；中途失败可能留下零份待审稿。短故事版应收进同一多文件事务。

## 最终建议

可以改，且值得改。

最稳妥的产品决策是：

1. 把现有项目视为“安全、可恢复的本地写作底座”。
2. 新建短故事领域层，不在卷章模型上长期打补丁。
3. 第一阶段只验证故事卡、蓝图、全篇生产、两次确认、交付检查和无伪卷章导出。
4. 平台规则使用版本化规则包；活动规则不写死。
5. 在实现前先补正文/审读/批准 hash 绑定和生产润色硬门。
6. 保留长篇 legacy 模式，不自动迁移、不破坏现有书仓。

这套路线能最大限度复用仓库已经做得最扎实的部分，同时避免把长篇连载的复杂度带进短故事产品。
